# Agrora website

Greek agricultural marketplace connecting producers with businesses. Visitors
browse and submit listings; authenticated administrators manage listings and images.

This repository contains the HTML, CSS, JavaScript, and PHP website. The Java
contact service is a separate project: [agrora-api](https://github.com/Chrispant/agrora-api).

## Requirements

- PHP 8.4 is the production target. PHP CLI is used for checks.
- PHP PDO with the MySQL driver, sessions, Fileinfo for image uploads, and
  Mbstring for report validation.
- MariaDB (production schema exported from 10.11) or a compatible MySQL server.
- Apache 2.4 with mod_rewrite and permission to apply the project's `.htaccess`
  rules. The clean URLs rely on Apache rewriting; PHP's built-in server alone
  does not apply those rules.

There is no frontend build step or Composer dependency installation in this project.

## Directory layout

```text
workspace/
├── agrora.gr/                    # This repository and Apache document root
│   ├── api/                      # Public PHP endpoints and protected admin API
│   ├── database/                 # Schema and optional fictional data
│   ├── data/                     # Crop, region, and variety catalogs
│   ├── images/                   # Tracked branding and static images
│   ├── js/
│   ├── tests/
│   └── uploads/listings/         # Runtime uploads; contents ignored by Git
├── private/
│   └── agrora-config.php         # Real configuration, outside this repository
└── agrora-api/                   # Optional separate clone of the Java service
```

Initialize Git inside `agrora.gr`, not around the whole workspace.

## Local setup

1. Configure an Apache virtual host with its document root pointing to this
   repository. Enable `.htaccess` overrides and mod_rewrite. With XAMPP, use an
   Apache virtual host rather than opening HTML files directly from disk.
2. Create an empty development database, for example `agrora_dev`, using
   `utf8mb4`, and a database user with a nonempty password and access to it.
3. Select that database in phpMyAdmin and import `database/schema.sql`.
4. Optionally import `database/seed.sql` into the development database. It creates
   ten fictional listings and no image records, exercising the placeholder image
   and pagination. Reimporting leaves existing rows with the same demo IDs unchanged.
   Dates and prices are illustrative and fixed; no production records are included.
5. Create a sibling `private` directory and copy `agrora-config.example.php` into
   it as `agrora-config.php`. Fill in the development database credentials and a
   hash generated by PHP's `password_hash($password, PASSWORD_DEFAULT)`. Use a
   private local/SSH tool with hidden password input, not a public hash-generator page.
6. Ensure PHP can read the private file and write uploads, its session directory,
   and its temporary directory. If `open_basedir` is configured, its allowed paths
   must include the private directory. Do not disable the restriction wholesale.
7. Visit the configured local hostname, check product browsing, then visit
   `/api/admin/admin-login.php` and use the password whose hash you configured.

The loader selects a private configuration by the on-disk document-root folder:

- `agrora.gr` reads `../private/agrora-config.php`.
- `elegant-visvesvaraya.213-158-90-234.plesk.page` reads
  `../private/agrora-test-config.php`, containing the separate test database credentials.

Unknown folder names fail closed. Keep the local checkout named `agrora.gr`;
additional deployment folder names must be explicitly added in `api/config.php`.
The test deployment never falls back to the live file if its own file is missing.
Selection does not depend on the request's Host header.
It does not load `.env` files or use the old `AGRORA_*` environment-variable fallbacks.
All six example keys are used: database keys must be nonempty strings, and the
admin hash must be a valid PHP password hash. Missing/invalid configuration returns
a generic service error; database connection failures are logged on the server.
Keep PHP error display disabled in production and inspect Plesk logs privately.

## Contact service

`js/contact.js` sends JSON containing `name`, `email`, and `message` to
`https://agrora-api-production.up.railway.app/api/contact`.
The Java service saves the message through Spring Data JPA and sends an email
notification through Resend. Its database and email credentials belong to that
service, not this website's configuration or SQL schema.

The frontend currently hardcodes the production URL. Until a configurable local
endpoint is added, submitting the contact form from a development copy attempts
to call the production service. Configure a local/test service before exercising
that form. Its CORS configuration must permit the exact development origin.

The inspected Java checkout also combines both production origins into one CORS
string; correcting those to separate arguments is pending in the API project.

## Authentication checks

From the repository root:

```sh
php tests/admin-api-auth.php
```

The test uses temporary files, isolated sessions, and a database stub. It checks
GET and POST requests across five admin endpoints for guest, expired, spoofed,
and authenticated session states (40 checks). Guests are rejected before the
database is reached. It does not test actual database mutations or email delivery.

Public browsing and `api/create-listing.php` do not require an admin login.
Admin read, update, delete, and image-management endpoints require a server-side
admin session. Authentication is separate from SQL injection protection and does
not constitute a complete security audit; CSRF and abuse protections need review.

## Production and Git boundaries

- Keep real configuration only in the sibling `private` directory. Never commit
  credentials, password hashes, production database dumps, or logs.
- Back up production database records and uploaded photos separately. Git tracks
  static images but ignores runtime files under `uploads/`.
- Plesk `.php-ini`, `.php-version`, `.well-known/` content, and the database
  diagnostic endpoint `api/test-db.php` are excluded. Ignore rules do not remove
  files from an existing server; do not publicly deploy the diagnostic endpoint.
- Deploy website code while preserving server configuration and uploads. Exclude
  `database/`, `tests/`, `.git/`, README, and the example configuration from the
  public deployment. The database/test directories also contain Apache deny rules;
  any server bypassing Apache must independently prevent access to those directories.
- Never import the development seed into production or reimport the schema over
  existing production tables. Future schema changes need deliberate migrations.
- After deployment, verify listings load, admin login/logout works, an existing
  listing opens for editing, and a logged-out admin API request returns HTTP 401.

The website repository is [Chrispant/agrora.gr](https://github.com/Chrispant/agrora.gr).
Deployment automation has not been configured; pushing to GitHub does not update Plesk.
